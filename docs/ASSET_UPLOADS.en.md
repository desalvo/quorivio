# Session assets — development status

Version: 0.1.0-dev. The new `POST /api/sessions/:id/assets` accepts a **raw binary request** (not multipart) with `Content-Type` and exact `Content-Length`. Authentication, approved presenter status and session ownership/co-presenter rights are required. Example:

```sh
curl -b cookies.txt --data-binary @slide.pdf -H 'Content-Type: application/pdf' \
  https://quorivio.example/api/sessions/SESSION_ID/assets
```

The response contains `id` and a presenter-authenticated retrieval URL (`GET /api/sessions/:id/assets/:assetId`). File signatures are checked; permitted types are PNG, JPEG, GIF, WebP, PDF, MP4 and WebM. The platform setting `max_upload_mb` defaults to 100 MB, with an upper bound of 1024 MB. The reverse proxy must have a compatible limit, as generated by the Kubernetes wizard. Binary data is stored under `QUORIVIO_ASSET_DIR` (Compose persistent volume `asset-data`), with metadata and SHA-256 in PostgreSQL.

**Not production-ready:** this initial implementation buffers each upload in server memory, does not include malware scanning, content sanitization, participant distribution, garbage collection after database deletion, quota management or remote/shared S3-compatible storage. Kubernetes deployments currently lack a corresponding shared assets volume. No claim is made that MIME signature checks alone make arbitrary documents safe. Store assets outside publicly served directories. Avoid multiple replicas until shared object storage and event coordination are complete. A complete instance backup must include both PostgreSQL and binary assets.
