# Quorivio RC322: Configurazione autenticazione / Authentication configuration

## Italiano
La pagina Dashboard → Impostazioni server → Backend di autenticazione e autorizzazione consente ai soli amministratori di piattaforma di configurare, salvare, testare e abilitare singolarmente i backend di login: interno, LDAP(S), Google OIDC, GitHub/Facebook OAuth e molteplici ulteriori provider OIDC (ad esempio AAI INFN). Ogni provider SSO attivato appare come scelta separata nella login. Il backend interno è sempre attivo; **ogni backend esterno è disabilitato per default**, anche quando variabili d'ambiente precedenti contengono già credenziali.

La configurazione persistente risiede in PostgreSQL ed è condivisa dalle repliche. Bind password e client secret sono conservati cifrati con AES-256-GCM, usando una chiave derivata da AUTH_SECRET; nessun endpoint di lettura restituisce i segreti in chiaro. Un campo segreto vuoto conserva la precedente credenziale. Proteggere e conservare AUTH_SECRET: una sua rotazione richiede una migrazione dei dati cifrati.

Per LDAP usare LDAPS con verifica del certificato, oppure LDAP con StartTLS obbligatorio; configurare bind DN/password di servizio, Base DN, filtro utente con {login}, attributi ID/email/gruppi, CA opzionale montata nel container, eventuale organizzazione e autoprovisioning. Il test LDAP esegue bind sicura e ricerca limitata; il login esegue comunque un bind con la password personale dell'utente. Per OIDC configurare issuer HTTPS, client ID, secret e callback HTTPS il cui percorso termina con /api/auth/oidc/ID/callback; il test verifica discovery e JWKS. Per GitHub/Facebook usare /api/auth/social/ID/callback; il test verifica solo la configurazione. Un vero login interattivo è richiesto per validare end-to-end le credenziali OAuth.

**MFA**: interno e LDAP dispongono ciascuno di un controllo per consentire la registrazione di TOTP o email MFA. I fattori già attivati continuano a essere richiesti nei login con password anche se si disabilita l'iscrizione di nuovi fattori, per evitare una regressione di sicurezza silenziosa. **Per le SSO l'MFA è responsabilità dell'Identity Provider**: Quorivio non richiede un secondo OTP/TOTP dopo l'accesso federato. Non collegare mai account in base alla sola corrispondenza email; mantenere un amministratore locale di recupero.

## English
Only platform administrators can configure and test authentication backends in Dashboard → Server settings → Authentication and authorization backends. The internal backend is always enabled. LDAP(S), any number of independent OIDC providers, and GitHub/Facebook OAuth are disabled by default, including legacy environment-configured providers. Enabled SSO providers appear as separate login options. Settings persist in PostgreSQL across replicas. Credentials are sealed with AES-256-GCM and never returned to the browser; an empty password field preserves the saved credential.

LDAP tests perform secure service bind and a limited search. OIDC tests validate discovery and JWKS; GitHub/Facebook checks are configuration-only and require interactive authorization for full verification. MFA enrollment (TOTP/email) can be enabled individually for internal and LDAP login. Existing password-login MFA remains enforced even if new enrollment is disabled. SSO delegates MFA to its IdP without a second app challenge. Keep AUTH_SECRET secure and maintain a local recovery administrator.
